## 三、突破：这台电视安装第三方 APK 的方法（已跑通）

TCL 有两道闸，必须都过：

| 闸 | 现象 | 解法 |
|---|---|---|
| ① ADB 安装总开关 | `install apk has be disabled from pm by system default!` | `setprop persist.tcl.debug.installapk 1` + `setprop persist.tcl.installapk.enable 1` |
| ② 桌面应用签名策略 | `INSTALL_PARSE_FAILED_INCONSISTENT_CERTIFICATES: disable install launcher app not signature by tcl` | 把 manifest 里 `android.intent.category.HOME` **等长替换**为 `HOMX`（本机不用标准 HOME 机制，去掉无副作用），再重签名 |

另外两个坑：

- **`.so` 必须 4096 字节对齐**（原包 `extractNativeLibs=false`），否则 `INSTALL_FAILED_INVALID_APK`；
- **`resources.arsc` 必须保持未压缩（STORED）**，否则资源读不到、界面黑屏；
- **不要手写 zip 打包器**：读回时字节不一致会导致签名校验失败。用 Python 原生 `zipfile` 重建 + `jarsigner` 签名 + `zipalign` 对齐最稳。

### 工具链（已就位）
```
C:\Temp 之外：
D:\Temp\jdk8\jdk8u504-b01\bin\{java,keytool,jarsigner}.exe
D:\Temp\bt\android-13\{zipalign,aapt,apksigner}.exe|.bat
\\\\192.168.123.6\\工作区\\platform-tools\\adb.exe
D:\Temp\plx.jks                      # 自签证书（storepass/keypass 均为 android）
D:\Temp\patch_sign.py                # 补丁+签名脚本（纯 Python）
D:\Temp\repack_align_sign.py         # 带对齐的打包脚本（.so 用）
```

### 安装流程（给桌面类 APK 用）
1. Python 重建：剥掉 `META-INF/*.SF|*.RSA|MANIFEST.MF`，manifest 打 HOME→HOMX 补丁，
   **每条目保持原 compress_type**（`resources.arsc` 尤其）；
2. `jarsigner -keystore plx.jks -storealg SHA256withRSA -digestalg SHA-256 -signedjar out.apk in.apk plx`
3. `zipalign -p -f 4 in.apk out.apk`
4. `adb push` 到 `/data/local/tmp/`，再 `adb shell pm install -r <路径>`（比 `adb install` 抗断线）

## 五、结论与后续选项

1. **换桌面在这台机器上被 TCL 明确禁止**（非 TCL 签名不允许装 launcher），现有绕过办法是"改 manifest + 重签名"，管线已跑通；
2. 但可用的桌面本身要满足 **无 GMS 依赖 + 兼容 Android 6**，目前试的两个都不满足；
3. 后续可选：
   - 继续试其它老一些的桌面（ATV Launcher / Wolf Launcher / 当贝精简版 / 旧版 Emotn）；
   - 或走 `persist.sys.bootpackage` 开机直进常用 App（TVBox / 飞牛影视），彻底绕开臃肿桌面；
   - 或刷社区 V039 精简包（内置 Emotn UI 桌面 + 去广告），代价是降级 + 刷机风险。

## 六、重要提醒

- `persist.sys.logd.level` 原本是 `S`（静默）、`persist.tcl.*` 两个安装开关原本是空；本次已按需修改并**把 logd 恢复为 S**；
- 系统会在应用恢复前台时自动改写 `persist.sys.bootpackage`，改动它之后要复查；
- 22 个包的冻结只影响 App 层，**系统分区未做任何修改**，不存在刷机风险。

### ⚠️ 一条重要教训：绝不能隐藏 `com.tcl.cyberui`

- `pm disable-user --user 0 com.tcl.cyberui` → **被拒**：
  `SecurityException: attempt to change component state ... uid=2000, package uid=1000`
  （它是 system 应用，shell 无权改其组件状态）
- `pm hide com.tcl.cyberui` → 命令成功，但**导致开机卡死**：
  `sys.boot_completed` 永远为空、`mCurrentFocus=null`、屏幕无任何界面。
  执行 `pm unhide com.tcl.cyberui` 后立即恢复（无需重启）。
- **结论：TCL 的开机流程依赖自带桌面，不可禁用/隐藏。**

### Home 键的限制（无 root 无法解决）

- Home 键被硬绑到 `com.tcl.cyberui`；
- `persist.sys.bootpackage` 由系统自动跟踪"最后恢复前台的 App"，按 Home 会被重置回 `com.tcl.cyberui`；
- 实际表现：**开机可能落在上次用的应用；但一旦按 Home 就回到 TCL 原桌面**；
- 第三方桌面的 `HOME` 类别被移除（否则装不上），所以系统不认它们是桌面。

## 九、性能天花板与超频结论

### 超频：不可行，且不建议（三层锁）

| 锁 | 实测证据 |
|---|---|
| **无 root** | `adb root` 失败；`echo performance > .../scaling_governor` → `Permission denied` |
| **上限写死在内核** | `cpuinfo_max_freq = 1500000`（内核 OPP 表的硬件描述，非配置项）。想超过必须重编内核，而 MStar 这颗电视 SoC 的内核源码 TCL 不公开 |

## 十、视频应用（OKTV）卡顿分析与替代方案

### OKTV 为什么卡

APK **81.7 MB**，内置了一整套重型运行时：

| 库 | 体积 | 作用 |
|---|---|---|
| `libijkffmpeg.so` | 13.3 MB | **FFmpeg 软解码器**（IJK 内核依赖它） |
| `libmedia3ext.so` | 6.7 MB | ExoPlayer 的 FFmpeg 软解扩展 |
| `libxl_thunder_sdk.so` | 5.6 MB | 迅雷 SDK |
| `libjpa.so` | 5.3 MB | |
| `libcronet.so` | 4.8 MB | Chromium 网络栈 |
| `libpython3.8.so` | 2.9 MB | **内嵌 Python 3.8 运行时** |
| `libquickjs-android-wrapper.so` | 1.3 MB | JS 引擎 |
| `libdav1dJNI.so` | 1.1 MB | AV1 软解码 |

- **界面卡**：应用体积与渲染开销大（海报墙 + 大量图片），叠加 A53 + MStar GPU + Android 6；
- **播放卡**：播放器内核若走 IJK，用的就是 `libijkffmpeg` **软解码**——A53 @1.5GHz 软解 1080p 必然掉帧。

### 芯片硬件解码能力（实测 `/system/etc/media_codecs.xml`）

- 视频硬解：H.264(AVC)、**H.265(HEVC)**、HEVC+Dolby Vision、VP8、VP9、MPEG2/4、H.263、VC1、WMV3、DivX、RealVideo、AVS
- 音频硬解：AC3、**DTS**、AC4、FLAC、AAC、MP3、Vorbis、LPCM、WMA、DRA
- **不支持 AV1**
- 结论：H.264/H.265 完全能硬解，"卡"通常是掉进软解，不是芯片不行。

### 已安装的替代方案

| 应用 | 包名 | 体积 | 说明 |
|---|---|---|---|
| 影视仓V3 3.0.36 | `com.mygithub0.tvbox0.osd_kitkat` | 28.2 MB | 专为老安卓编译（包名含 kitkat），minSdk 16 / targetSdk 26，与 OKTV 共存 |
| MX Player Pro 1.94.0 | `com.mxtech.videoplayer.pro` | 42.9 MB | 外部播放器，硬解 |

> 来源：GitHub 社区仓库 `youhunwl/TVAPP`，非官方商店；MX Player 为去广告 Mod 版。
> 两者均不声明 HOME 类别，无需打补丁即可安装。

### 建议操作

1. OKTV → 设置 → 播放器：内核换 **EXO**（走 MediaCodec 硬解），**别用 IJK**；或把"外部播放器"设为 MX Player；
2. 插网线（本机有 RJ45），避免 WiFi 成为高码率瓶颈；
3. 片源避开 AV1 与 4K 高码率；
4. OKTV 设置里关闭 DLNA/投屏接收 → 退出后不再常驻后台。

## 十二、安全发现：`tcl.ISeekerService` 存在未授权 root 命令执行（已实测验证）

> 发现时间：2026-10-21 · 性质：本地提权（uid 2000 → root）· 状态：**已验证，未利用**

### 12.1 调用链

```
shell (uid 2000)
  │  service call tcl.ISeekerService 1 s16 <命令>
  ▼
tcl.ISeekerService
  （/system/lib64/libseekerservice.so，由 root 进程 sserver 注册到 servicemanager）
  ▼
SeekerService::execute(String8)  →  procCmdUseForkExec()
  ▼
fork() + execve("/system/bin/sh", "-c", <命令>)      ← root 身份
```

### 12.2 已验证的 PoC

```bash
adb shell "service call tcl.ISeekerService 1 s16 \$'\xe6\x91\xa9\xe6\x91\xa9'"
```

返回的 Parcel 内容：

```
0x00000000: 00000400 3d646975 6f722830 2029746f   '....uid=0(root) '
```

`uid=0(root)` —— 从 shell 用户拿到 root 执行结果。code 2 返回退出码 `0`。

### 12.3 为什么命令要写成 `搩搩`

服务端把 Parcel 里的 **String16 当成 String8 读**：

| | 发送方（String16） | 接收方（String8） |
|---|---|---|
| 长度字段 | 码元个数 N | 字节数 N |
| 内容 | N × 2 字节（低字节、高字节交错） | 前 N 字节 |

于是直接发 `s16 id`（2 个码元）→ 读到 2 字节 `69 00` → 在 NUL 处截断成 `i`。

**构造规则**：要执行长度 m 的命令，需发 **m 个码元**，其中前 ⌈m/2⌉ 个码元携带命令字节：

```
码元 i = 命令字节[2i] | (命令字节[2i+1] << 8)
```

`"id"` = `0x69 0x64` → 第 1 个码元 = `0x6469` = `搩`（UTF-8 `E6 91 A9`）；第 2 个码元只占位。

### 12.4 三个独立缺陷叠加

1. **无权限校验**：`execute(String8)` 的尾调用直接是 `procCmdUseForkExec`，既不经过 `checkCmdLevel`（命令分级白名单），也没有调用 `auth()`。只有 `execute(level, cmd)` 重载才查白名单。
2. **类型混用**：String16 写、String8 读。这本身是 bug，同时正好成为绕过手段。
3. **白名单本身可碰撞**：`checkCmdLevel` 用 Adler-32 校验命令哈希，理论上可构造碰撞。本次未用到。

### 12.5 影响面

- 任何能在本机执行 shell 的入口（ADB 调试、或任意应用经 binder）都能直接拿到 root。
- **本机 ADB over TCP 5555 常开**（`persist.adb.tcp.port=5555`）→ 同网段任何人都能 root。
- 无法通过冻结/卸载规避：服务由 root 进程 sserver 在启动时注册。

### 12.6 建议

| 场景 | 措施 |
|---|---|
| 日常使用 | 关闭"开发者选项 → USB 调试"，或断开 ADB 网络暴露 |
| 网络隔离 | 电视单独 VLAN / 访客网络，不与不可信设备同段 |
| 官方修复 | 需固件更新；本机 `V8-S38AS13-LF1V041` 已是官方最高版本，**无解** |

### 12.7 本次未做的事

- 未通过该通道执行任何修改性命令（仅 `id` 验证身份）
- 未安装 su、未改动系统分区、未修改任何系统文件

> 该通道足以实现完整 root。但结合第 11 节的结论，root 对本机"卡顿"的边际收益很低，
> 且本机无官方救砖包，不建议利用。

### 13.4 怎么做出来的

限制：`tcl.ISeekerService` 把 String16 当 String8 读，所以要执行长度 m 的命令，必须发 m 个码元，前 ceil(m/2) 个码元携带命令字节（`码元[i] = 字节[2i] | 字节[2i+1] << 8`）。脚本 `D:\Temp\rootexec.py`，`build_arg()` 负责构造。

```bash
# 每一步都是一次 service call
dd if=/dev/block/mmcblk0p16 of=/data/local/tmp/bk_system.img bs=1048576 2>&1
chmod 644 /data/local/tmp/bk_*.img     # 否则 adb pull 报 remote Permission denied
adb pull /data/local/tmp/bk_system.img <本地路径>
```

坑：这版 toybox 的 `dd` **不支持 `bs=1M` 后缀**，只认纯数字（`bs=1048576`），写 `1M` 报 `illegal number`。

### 13.5 怎么恢复

前提：root 通道还在（第十二节），或者能进 recovery。

```bash
# 单个分区回写，例：恢复 system
dd if=/data/local/tmp/bk_system.img of=/dev/block/mmcblk0p16 bs=1048576
sync
reboot
```

注意：

- **分区号必须对**。写错分区等于变砖，写之前再确认一遍 13.2 的表。
- `system.img` 是 ext4 原始镜像，直接 `dd` 回去即可，不需要 `mount -o loop`。
- 回写顺序：先 `boot` / `tvos` / `system`，最后 `persist` / `tclconfig`（这两个影响开机配置，放最后，避免中途出问题时状态不一致）。
- `persist` 里存着 `persist.sys.bootpackage` 等属性。如果桌面起不来，单独回写 `persist` 通常能救回来。

### 13.6 有了这个备份意味着什么

改 `/system` 不再是单向操作。改坏了 `dd` 回去，2GB 按 26MB/s 算约 80 秒。

这是后续任何系统层改造（去广告、替换桌面、精简 framework）的前置条件。

## 十五、把 tvhome 装成系统桌面（2026-10-21 18:20）

### 15.1 目标
Aerial / Wolf / tvhome 三个第三方桌面里，tvhome 最轻（30 MB PSS）且全中文，但要让它当**真正的默认桌面**（开机直接进、Home 键回得去），必须绕开 TCL 的两道闸。唯一可行路径：作为**系统应用**放进 `/system/app`，由 PackageManager 开机扫描注册，不走 `pm install`。

### 15.2 步骤
1. 源码把 `AndroidManifest.xml` 的 `HOMX` 改回 `HOME`（之前的 HOMX 只是为绕安装闸），`gradlew assembleRelease` 重新出包（651,415 B）。
2. `mount -o rw,remount /system`（root 通道）。
3. `mkdir /system/app/TvHome` → `cp` APK → `chmod 644`。
4. `chmod 755` 目录、`chcon -R u:object_r:system_file:s0`。
5. `mount -o ro,remount /system` → `reboot`。

### 15.3 关键坑：root 通道 mkdir 出来的目录是 700
第一次放进 `/system/app` 时开机直接**卡在开机动画**（`sys.boot_completed` 一直为空，且 `pm list packages` 只有 80 个包）。

日志给出的真实原因：
```
W/PackageManager: chyj scanDirLI File to parse /system/app/TvHome
W/PackageManager: Failed to parse /system/app/TvHome: No packages found in split
```
`No packages found in split` 不是签名问题，是**扫描器读不到目录里的 APK**。用 `ls -Zd` 一看：`opendir failed, Permission denied` —— root 通道里 `sh` 的 umask 是 077，`mkdir` 出来的目录权限 `drwx------`，PackageManager（system uid）进不去，于是"目录里没有包"。

修复：`chmod 755 <目录>` + `chmod 644 <apk>` + `chcon u:object_r:system_file:s0`，重启即被正常扫描。

**教训**：往 `/system` 里手工放应用，权限和 SELinux 上下文必须显式设定，不能靠默认值；出问题先看 `ls -lZ`。

### 15.4 结果（已重启验证）

- 开机 `mResumedActivity = com.gathin.tvhome/.MainActivity`（45 s 完成开机）

- Wolf 的系统目录已移除，`/system/app` 里只保留 TvHome 一个第三方桌面

## 十六、OKTV 空闲自动清理（2026-10-21 18:55）

### 16.1 问题
`com.fongmi.android.tv`（OKTV 5.1.6）退出到桌面后进程常驻，后台跑 `DLNARendererService`，实测占整机约 4% CPU。它的 `PlaybackService`（媒体键）不能禁——禁了遥控器播放/暂停失效；prefs 里也没有 DLNA 开关（全表只有 `background=1` 一个相关项）。

### 16.2 方案：按 oom_score_adj 判定"是否在前台"，空闲即 force-stop
Android 6 里进程的 `/proc/<pid>/oom_score_adj` 能可靠区分可见性：前台 0，可见/可感知 100–200，缓存态 400+。实测 OKTV 退到桌面后 `oom_score_adj = 411`。

在开机脚本 `/system/bin/cpu_dvfs_scaling.sh` 里加了一个循环（插在原有超频 keeper 循环后面）：

```sh
(sleep 40; while :; do p=$(pgrep com.fongmi.android.tv);
  if [ -n "$p" ]; then a=$(cat /proc/$p/oom_score_adj 2>/dev/null);
    if [ "${a:-0}" -ge 300 ]; then am force-stop com.fongmi.android.tv; fi;
  fi; sleep 60; done) &
```

- 每 60 s 检查一次，`oom_score_adj >= 300` 即视为"不在前台"，直接 force-stop。

## 十七、桌面「设置」入口修复（2026-10-21 18:52）

### 17.1 现象
tvhome 首页右上角齿轮「设置」点下去弹一句 **「此电视不支持该功能」**，什么都不打开（用户 2026-10-21 反馈）。

### 17.2 根因（两道）
1. **本机没有任何应用接收标准 Settings 动作。** 设备端逐个试过：`android.settings.SETTINGS`、`.DISPLAY_SETTINGS`、`.WIFI_SETTINGS`、`.MANAGE_APPLICATIONS_SETTINGS`、`.APPLICATION_SETTINGS`、`.DEVICE_INFO_SETTINGS`，`am start` 全部 `unable to resolve Intent`。TCL 的 `com.tcl.settings` 只注册自家 action，没有实现 AOSP 的标准入口（它压根不是 AOSP Settings 改的）。
2. **原代码的小米兜底是个陷阱。** `MainActivity.systemIntent()` 里第二顺位硬编码了 `com.xiaomi.mitv.settings/.entry.MainActivity`，并用 `intent.resolveActivity(pm) != null` 判断"能不能开"。本机没装这个包，但 `resolveActivity` 对**显式组件**仍返回非 null → 代码以为能开，把 Intent 交给 `startActivity`，AMS 才报 `Error type 3: Activity class does not exist`，异常被 `open()` 的 catch 捕获 → 弹「此电视不支持该功能」。**用 resolveActivity 预判显式组件在这台机器上不可靠。**

### 17.3 修法
不再"先问再开"，改成"开了失败再兜底"：

```java
// Compat.java
static boolean startWithFallback(Context ctx, Intent target) {
    try { ctx.startActivity(target.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)); return true; }
    catch (ActivityNotFoundException ignored) { }
    Intent tcl = new Intent().setComponent(
            new ComponentName("com.tcl.settings", "com.tcl.settings.MainActivity"));
    try { ctx.startActivity(tcl.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)); return true; }
    catch (ActivityNotFoundException e) { return false; }
}
```

- `MainActivity` 里 4 处「打开设置」的调用（顶部 WiFi 胶囊、顶部齿轮、设置键、WiFi 胶囊兜底）统一走新方法 `openSettings(String action)`，全部改调 `Compat.startWithFallback`；删掉了不可靠的 `systemIntent()` 与小米兜底。
- `QuickSettingsActivity.addRow()` 的每一行（电视设置/图像/网络/应用）同样改调 `Compat.startWithFallback`，失败才弹 toast。

### 17.4 实测（logcat 取证）
- 点齿轮 → `START u0 {act=android.settings.SETTINGS} from uid 10066`（失败）→ 紧接着 `START u0 {cmp=com.tcl.settings/.MainActivity}`（成功）。
- 电视上出现 TCL 原生设置浮层：**显示（背光亮度 35）/ 声音 / 网络 / 蓝牙与外设 / 系统**，可按遥控操作，BACK 关闭回桌面（`dumpsys window windows | grep -c com.tcl.settings` → 0）。
- 点 WiFi 胶囊 → `act=android.settings.WIFI_SETTINGS` 失败 → 同样落到 `com.tcl.settings/.MainActivity`。

### 17.5 部署
与第十五节同法：`adb push` 到 `/data/local/tmp`，root 通道 `mount -o rw,remount /system` → `cp` 覆盖 `/system/app/TvHome/TvHome.apk` → `chmod 755` 目录、`chmod 644` APK、`chown root:root`、`chcon u:object_r:system_file:s0` → `mount -o ro,remount /system` → 重启。重启后 `sys.boot_completed=1` 用时 27 s，`md5sum` 与本地一致（8c227760ebcf98ec31b38c1bbfdfe281）。

### 17.6 备注
- 编译期踩坑：`addRow()` 里把参数 `target` 重新赋值后，方法内的 lambda 捕获该变量 → `error: 从 lambda 表达式引用的本地变量必须是最终变量`。改成 `final Intent go = ...` 即可。
- `com.tcl.settings` 的主入口只有一个 `MainActivity`，显示/声音/网络都是它内部的分栏，没有独立 Activity 可深链。想要直接跳到某一栏，只能在 TCL 设置出现后用 DPAD 导航。
- 回滚：把 `东芝65U6900C-备份` 里的旧包或 `TvHome-gathin-API23-patched.apk` 推回 `/system/app/TvHome/TvHome.apk` 重启；本节改动只涉及 APK 内部，不碰系统其它文件。

## 二十一、遥控器语音键改造成「语音键盘」（2026-10-21 23:05）

**目标**：在 OK影视、搜索框等任何输入框里，按遥控器语音键说话，文字直接进输入框；不依赖电脑、不依赖 NAS。

### 21.1 结论

识别在电视本地跑（讯飞云端引擎，助手本来就在用），PC 上的 whisper 服务已停用、相关探针 App 已卸载。
最终形态：`com.iflytek.sample.view`（输入法 + 代理服务），长按语音键 → 说话 → 文字进框，**不弹助手、不播报、不跳搜索页**。

### 21.2 链路（实测证据）

1. 物理语音键 → TCL 框架注入厂商键码 **4113**（`WindowManager: interceptKeyTq keycode=4113`），同时投递给「当前输入法」和「语音助手」两条路。
2. **4113 只有助手栈（com.iflytek.xiri）活着时才会派发到输入法**。`am force-stop com.iflytek.xiri` 之后，注入 4113 只停在 `interceptKeyTq`，`interceptKeyTi` 不出现，输入法收不到（`RELAY: voice key down` 无日志）。所以助手进程必须保留。
3. **麦克风被助手独占**：助手录音期间，其他进程 `AudioRecord.read()` 直接返回 0（同一时刻助手进程刷 `AudioRecord-JNI: Error -110`）。自建 App 想自己录音拿不到数据 —— 这条路放弃。
4. 助手的识别结果走 **`tv.yuyin.view.aidl.IVoiceViewAidlInterface`** 通道下发（Bundle 里 `action=10005 SHOWUSERTEXT` / `10020 SHOWUSERTEXTFLOW`，文字在 `obj`）。

6. 代理把每次调用原样转发给 `com.tcl.walleve`，所以原助手功能不被破坏；把 `com.tcl.walleve` 冻结后，播报/悬浮窗/搜索页全部消失，文字照常到代理。

- 点它直接进直播；返回键退出回 Aerial。

### 27.7 黑屏的真正原因（2026-10-30 下午定位）
症状：`/txt` 订阅正常、播放器 `prepared`、解码器 `MSTAR_VDEC_DBG` 稳定 25 fps，但屏幕全黑、`screencap` 也全黑。

根因在 **VideoView 的测量**，不在源、不在解码：

- `VideoView.onMeasure` 默认按视频宽高比缩小自己：父容器 1470 宽、视频 16:9 → 高度 **826**；
- MStar 的 `SurfaceView.surfaceChanged` 里有一条判断，surface 尺寸不够就不发 `com.tcl.video.fullscreen` 广播（logcat 原文 `width <800 || height <600; send com.tcl.video.fullscreen broadcast=false`）；
- 没有这个广播 → `sys.video.fullscreen=false` → 视频层不进显示通路 → 黑屏；
- 同时窗口层是整屏 `1920x1080`（`FB SKIP`），把下面的 SurfaceView 层完全盖住。

修复：给 VideoView 覆盖 `onMeasure`，强制用父容器尺寸：

```java
video = new VideoView(this) {
    @Override
    protected void onMeasure(int widthMeasureSpec, int heightMeasureSpec) {
        setMeasuredDimension(
                MeasureSpec.getSize(widthMeasureSpec),
                MeasureSpec.getSize(heightMeasureSpec));
    }
};
```

修完的 SurfaceFlinger 变成：

```
HWC | SurfaceView                  | 450, 0, 1920, 1080   ← 视频层占满右侧全高
FB SKIP | com.local.livetv/...     |   0, 0,  450, 1080   ← 窗口层只剩左侧列表
```

窗口在视频区域真正"挖洞"了，画面立刻出来（实测 CCTV-1 正常）。

**教训**：这台机器上视频黑屏要按这个顺序查——① logcat 找 `com.tcl.video.fullscreen` 是 true 还是 false；② `dumpsys SurfaceFlinger` 看 SurfaceView 层的高度和 MainActivity 层是不是整屏；③ 再怀疑源。这一条同样适用于以后任何自建播放器。

### 27.17 Home 键修复：自己写一个无障碍服务抢键（2026-10-30 17:10）
27.16 说"修不了"，那结论下早了。**用户让再想想办法**，于是读了 Aerial 的 `HomeGuardService.kt` 源码，找到两条可走的路。

**为什么 Aerial 接管不了**
1. Aerial 的 `updateKeyFilter()` 会在条件不满足时**主动关掉**按键过滤。实测日志：
   ```
   16:53:36.830  filtering keys
   16:53:36.838  stopped filtering keys   ← 6 ms 后自己关了
   ```
   条件是 `!keysPassThrough && !screenOff && !padGame && (SDK<=R || aerialInFront)`，其中 `padGame` 依赖 `gamepadAttached`（用 `supportsSource(SOURCE_GAMEPAD)` 判定）。
   本机 `dumpsys input` 里 **`sim-mouse` 的 sources = 0x2703，含 SOURCE_GAMEPAD(0x401)**，于是被误判成手柄 → 有别的 App 在前台时过滤就被关掉。
   Aerial 源码注释里点名过同一类 bug（Sony 的 `virtual-search` 设备被当成手柄）。
2. Aerial 的服务带 `accessibilityFlags=flagDefault`，Android 6 的按键分发里 default 服务优先。

**解法：自己写一个无障碍服务**
新 App `com.local.homekey`（12.7 KB），只做一件事：

```java
// 1) 监听系统处理 Home 键时发的广播
IntentFilter f = new IntentFilter("android.intent.action.CLOSE_SYSTEM_DIALOGS");
registerReceiver(homeBroadcast, f);
// 2) 收到 reason=homekey 就把 Aerial 拉回前台
Intent i = new Intent(Intent.ACTION_MAIN);
i.addCategory(Intent.CATEGORY_HOME);
i.setComponent(new ComponentName("app.orchard.tv", "app.orchard.tv.MainActivity"));
i.addFlags(NEW_TASK | RESET_TASK_IF_NEEDED | SINGLE_TOP);
startActivity(i);
```

**关键**：TCL 的 `startDockOrHome` 虽然硬编码去启动坏掉的 `com.tcl.cyberui/.MainActivity`，但它**仍然会发 `ACTION_CLOSE_SYSTEM_DIALOGS` 且 reason=homekey**（PhoneWindowManager 的标准行为）。所以不必去拦按键，只要接这个广播——系统发给所有注册者，绕开了按键过滤的分发顺序问题。

实测：
```
HomeKey : CLOSE_SYSTEM_DIALOGS reason=homekey
HomeKey : homekey broadcast; bringing Aerial to front
focus: app.orchard.tv/app.orchard.tv.MainActivity
```
**重启后依然有效**（两个无障碍服务都在 `enabled_accessibility_services` 里）。

**踩的坑**
- `canRequestFilterKeyEvents=true` 只写在 manifest 不够，运行时还要 `serviceInfo.flags |= FLAG_REQUEST_FILTER_KEY_EVENTS` + `setServiceInfo(info)`；
- manifest 里的 `accessibilityFlags` 要写 `flagRequestFilterKeyEvents`（Android 6 里这个枚举值 = 32），写 `0` 会编译报错；
- aapt2 链接时自建 `string/desc`、`string/app_name` 会和 framework 资源冲突（"does not override an existing resource"），要加前缀（本项目用 `hk_`）；
- d8.bat 需要 `JAVA_HOME`；构建目录要用绝对路径，否则在 UNC cwd 下会跑到别处。

**遗留**：`com.tcl.cyberui` 现在是 `installed=false`（我 `pm uninstall --user 0` 造成的），Home 键不再去找它。要还原：`adb shell pm install --user 0 -r /system/priv-app/CyberUI/CyberUI.apk`（会装回 3.2.00 那份，启动仍崩，但至少不会再被系统找不到）。
## 二十九、电视卡死事故：MStar HEVC 硬解的 flush 崩溃（2026-10-30 18:56）

### 29.1 现象
19:00 前后整台电视黑屏、按什么都没反应。adb 还能连：

```

```

重启后更糟：卡在开机动画，`sys.boot_completed` 一直是空、`service.bootanim.exit=0`、`persist.sys.bootpackage=com.fongmi.android.tv`。

### 29.2 根因（两层）

**第一层：OK影视 播 H.265 时把硬解解码器搞崩了**

```
pid: 11030, tid: 23620, name: CodecLooper  >>> com.fongmi.android.tv <<<
V ACodec  : [OMX.MS.HEVC.Decoder] signalFlush
V ACodec  : [OMX.MS.HEVC.Decoder] FlushingState onOMXEvent(0,1)
V ACodec  : [OMX.MS.HEVC.Decoder] dequeued buffer 0x55c3796080
F libc    : Fatal signal 11 (SIGSEGV), code 1, fault addr 0x70 in tid 23620 (CodecLooper)
```

`fault addr 0x70` = 空指针 + 成员偏移。**MStar 的 HEVC OMX 组件在 `flush` 回调里还要 `dequeue buffer`，而此时上层已经 `release` 了对象** —— 闭源固件里的生命周期 bug。

**第二层：开机被这个崩掉的 App 拖住**

`persist.sys.bootpackage` 指向 `com.fongmi.android.tv`（TCL 在应用 resume 时改写它）。重启后系统等这个包，而它的 `DLNARendererService` 又崩又重启，`bootanim` 永不退出 → `sys.boot_completed` 不置位 → 死锁在开机动画。

### 29.3 救治
```bash
adb shell setprop service.bootanim.exit 1        # 放开机动画走
adb shell am start -n com.fongmi.android.tv/.ui.activity.HomeActivity   # 让 bootpackage 起来
adb shell am start -n app.orchard.tv/.MainActivity                      # 回 Aerial
```
之后 `sys.boot_completed` 立刻变 1。

**注意**：`service.bootanim.exit` 是 system 属性，只有 shell/adb 能改，普通 App 改不了 —— 所以做不了"App 侧看门狗"，只能在电脑上救。

### 29.4 处置：换 teardown 路径，不降画质
OK影视（FongMi 5.1.6 / leanback-arm64_v8a）的播放设置里：

| 项 | 原值 | 改为 | 说明 |
|---|---|---|---|
| 播放核心 | **EXO** | **系统** | ExoPlayer 1.10.0 显式 `flush()` 后立刻 `release()`，正好踩中固件 bug |
| 解码方式 | 硬解 | 硬解 | **不动**，H.265 硬解保留 |
| 渲染方式 | Surface | Surface | 不动 |

依据是实测对比 —— **同一个 `OMX.MS.HEVC.Decoder`，两条路径两种结果**：

| 播放器 | 解码路径 | H.265 下反复切台 |
|---|---|---|
| livetv（MediaPlayer + VideoView） | 系统 MediaPlayer → 厂商 OMX 封装 | 几十次，**没崩** |
| OK影视（ExoPlayer） | MediaCodec 直接驱动 | `signalFlush` 后 3 ms **崩** |

### 29.5 为什么不用软解
4×Cortex-A53 1.5 GHz 软解 1080p H.265 没有实用价值（必卡）。**保留硬解、只换 teardown 路径**才是正解。

### 29.6 备选与遗留
- OK影视 还有第三档内核 **IJK**（B 站 ijkplayer，ffmpeg 内核，teardown 自己实现），功能接近 EXO，**未实测**是否躲得过这个 bug；
- 三档循环顺序：EXO → 系统 → IJK → EXO；
- 若哪天系统核心遇到不支持的格式，可临时切 IJK/EXO，但要有"再卡死一次"的准备；
- 我们的 livetv 一直走 MediaPlayer，**不受影响**。
### 29.7 调参过程与最终结论（2026-10-30 20:10）

试过的每个组合，都记下来，免得以后重走：

| 组合 | 结果 |
|---|---|
| EXO + 硬解 + 隧道**关闭** | **崩**（`signalFlush` → SIGSEGV，就是 29.2 那次） |
| EXO + 硬解 + 隧道**开启** | **不崩但画面全黑**。日志确认 MStar 真的进了隧道模式：`D MS_OMX_VDEC: Tunneled Resolution Change 0x0 to 1920x1080`，音频正常（`OMX.google.aac.decoder` 持续工作），但视频层不出画。**MStar 的 tunneled 路径和 Surface 渲染不兼容**，这条路走不通 |
| 系统 + 硬解 | **正常**，切台几十次不崩 |
| 三档循环顺序 | EXO → 系统 → IJK → EXO |

**为什么"换个版本"大概率没用**

ExoPlayer 2.x 和 media3 1.x 的 `MediaCodecRenderer.releaseCodec()` 都是同一个模式：先 `flush()` 或 `stop()`，再 `release()`。这个模式从 2017 年至今没变过，而崩溃恰好发生在 `signalFlush` 之后的 `dequeued buffer` —— 换版本只是换 ExoPlayer 的版本号，这段逻辑不动，所以不解决问题。

**真正不同的是 IJK**：ijkplayer 的 native 层（ffmpeg + 自己的 video render）管理 codec 生命周期，teardown 时更保守，理论上有机会躲开，但本机未实测。

**为什么不能软解**：4×Cortex-A53 1.5 GHz 软解 1080p H.265 会卡成幻灯片，没有实用价值。

### 30.8 IJK 压测结果：IJK 干净，EXO 仍崩（2026-10-31 01:32）

对 OK影视 切换内核后的实测（`logcat -c` 后重新计数）：

**IJK 部分 —— 通过**

12 轮「播放→退出」压测 + 3 轮快速压测，**零崩溃**。
IJK 的 teardown 顺序是 `shutdown_l()` → `dec_ref(): ref=0` → `finalize` → `release`，比 ExoPlayer 保守，躲开了固件 bug。

**EXO 部分 —— 仍然崩**
```
I ExoPlayerImpl: Release 34872ad [AndroidXMedia3/1.10.0]
V ACodec: [OMX.MS.HEVC.Decoder] signalFlush
V ACodec: [OMX.MS.HEVC.Decoder] Now Flushing
V ACodec: [OMX.MS.HEVC.Decoder] FlushingState onOMXEvent(0,1)
V ACodec: [OMX.MS.HEVC.Decoder] dequeued buffer 0x5594b5b1a0
F libc: Fatal signal 11 (SIGSEGV), code 1, fault addr 0x70 in tid CodecLooper
```

**关键结论**：把 OK影视 的播放核心设成 IJK **并不能覆盖全部源** —— 它对某些源（B 站等）会自动回退到 ExoPlayer，一回到 EXO 就崩。

**三种内核的最终结论**：

| 内核 | teardown 顺序 | H.265 硬解 | 结果 |
|---|---|---|---|
| ExoPlayer 1.10 | `flush()` → `release()` | 是 | **崩**（3ms 内 SIGSEGV） |
| IJK（ijkplayer） | `shutdown_l()` → `dec_ref()` → `release` | 是 | **不崩**，但部分源会自动回退到 EXO |
| 系统 MediaPlayer | `stopPlayback()` → `release()` | 是 | **不崩**（livetv 实测几十次切台） |

**唯一能彻底避免的**：让 App 完全不走 ExoPlayer —— 即播放核心选「系统」。代价是字幕/多音轨能力弱一些。

**另外一个收获**：这次崩溃发生时 App 死了，但系统**没有**跟着黑屏 —— 因为崩溃时 Aerial 在前台（压测前已按 Home 退出）。说明崩溃本身不致命，**致命的是崩溃时 App 独占前台 + bootpackage 指向它**。

### 30.9 为什么只有系统 MediaPlayer 躲得开

MStar 的 `OMX.MS.HEVC.Decoder` 在 `flush` 回调里还要 `dequeue buffer`，如果此时上层已经把组件 `release` 了，就会解引用空指针（`fault addr 0x70`）。

- ExoPlayer / IJK 都是**直接持有 MediaCodec**，切源时显式 `flush()` 后立刻释放 → 踩中；
- 系统 MediaPlayer 走的是厂商封装的 OMX 代理，`stopPlayback()` 内部有更保守的同步，不出现「flush 未完成就释放」的窗口。
